Serial, parallel and custom execution#

Two independent choices decide how the subproblems of an outer iteration are solved:

the sweep

which coordinator state each subproblem sees: gauss_seidel (each solve uses the copies updated by the previous solves of the same outer iteration) or jacobi (all solves start from the same snapshot);

the executor

where the solves run: inprocess, process (a pool of worker processes), a remote service, or any object with map(fn, tasks) and close().

mode picks a common combination, and sweep= and executor= override it:

MDAO.run(file, mode="serial")                          # Gauss–Seidel, in this process (default)
MDAO.run(file, mode="parallel")                        # Jacobi, one worker process per subproblem
MDAO.run(file, sweep="jacobi", executor="inprocess")   # Jacobi without worker processes
MDAO.run(file, sweep="jacobi", executor=my_executor)   # Jacobi on your own back end

The same options are accepted by Session (Session.from_yaml(..., mode="parallel")).

Which sweep?#

Gauss–Seidel propagates information within an outer iteration and usually needs fewer outer iterations. Jacobi solves all subproblems concurrently, so an outer iteration takes as long as the slowest subproblem instead of the sum of all of them; it pays off when the subproblems are expensive and of similar cost. The two sweeps follow different paths and in general end at different, equally consistent designs.

Same answer, whatever the execution order#

In a Jacobi sweep every subproblem starts from the same snapshot, and the results are merged in subproblem order, each subproblem contributing only the copies it owns. The outcome therefore does not depend on which worker finishes first. The regression suite checks that a Jacobi run gives bit-identical results when its subproblems are solved in process, in reversed order, with the results returned out of order, and in a process pool.

Solving the tasks in your own process pool#

examples/ask_tell_process_pool.py uses Session’s ask/tell interface with a concurrent.futures.ProcessPoolExecutor; any other scheduler (Dask, Ray, a job queue, another framework’s parallel evaluator) is used the same way:

import os
from concurrent.futures import ProcessPoolExecutor

from basic_disciplines import BLACKBOXES

from DMDO import Session, load_setup, solve_task

HERE = os.path.dirname(os.path.abspath(__file__))


def main():
  data = load_setup(os.path.join(HERE, "basic_problem.yaml"))
  data["coord"]["c1"]["budget"] = 8
  data["MDO"]["display"] = False     # no per-iteration console lines
  with Session.from_dict(data, working_dir=os.path.join(HERE, "_runs"), mdo_name="pool", blackboxes=BLACKBOXES,
                         sweep="jacobi") as session, ProcessPoolExecutor(max_workers=2) as pool:
    while not session.done:
      tasks = session.ask()
      record = session.tell(list(pool.map(solve_task, tasks)))
      if record is not None:
        print(f"iteration {record.iteration}: max|q| = {record.max_inconsistency:.3e}")
    print(session.result().to_dict()["variables"])


if __name__ == "__main__":  # required for process pools on Windows/macOS
  main()

The final design is exactly the one of the in-process Jacobi run of The Session API (objective 4.337014798880885) and of the remote workers of The HTTP service and remote workers: three different execution back ends, one answer.

Important

Worker processes import the analyses and objectives by reference, so they must be defined at module level in an importable module (here basic_disciplines.py), and the script needs the if __name__ == "__main__": guard on Windows and macOS.

A custom executor#

An executor is any object with map(fn, tasks) returning the results in task order, and close(). Register a factory under a name to select it with executor="<name>":

from DMDO import InProcessExecutor, executors

class CountingExecutor(InProcessExecutor):
    """Solves tasks in this process and counts them."""

    def __init__(self, max_workers=None):
        self.solved = 0

    def map(self, fn, tasks):
        self.solved += len(tasks)
        return super().map(fn, tasks)

executors.register("counting", CountingExecutor)

session = Session.from_yaml("problem.yaml", executor="counting", blackboxes={...})

A factory is called as factory(max_workers=n). Executors given as instances are not closed by DMDO; executors created from a name are closed at the end of the run.
